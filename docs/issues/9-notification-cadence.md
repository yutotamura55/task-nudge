# Issue #9: 通知を継続して届け、未対応分を残す

## 利用者が求める動作

通知時間中は設定間隔ごとに通知を1件追加する。複数の候補タスクがある場合は、まだ通知していない別のタスクを先に知らせる。通知を見逃した場合、同じタスクも再通知できる。処理が遅れても、過去の回数分をまとめて通知しない。

ユーザーは数分程度のずれを許容するが、3時間で1〜2件しか届かない状態を避けたい。目覚まし音・専用画面は使わず、従来の通常通知を使う。省電力制御や端末メーカーの制限があるため、15分ごと・3時間以内の件数を全端末で保証する仕様ではない。

## 観測した原因

旧実装の `ReminderEngine.evaluate()` は1件でも active 通知があると新規通知を止める。さらに `AndroidNotificationGateway` は固定 ID で `notify()` するため、複数回呼んでも前の通知を置き換える。15分を設定しても、旧設計の「通知は同時に最大1件」が件数を制限していた。

旧スケジューラーは15分周期の WorkManager のみを継続経路に使う。Android は Doze 中に通常の JobScheduler 処理を延期するため、スリープ中の短い通知間隔には適さない。[Android の Doze 説明](https://developer.android.com/training/monitoring-device-state/doze-standby)

## 今回の設計

- 各通知に個別の OS ID とランダムな token を割り当て、Room の `active_reminders` に保存する。既存 DB の version 1 から version 2 へ移行すると、表示中だった旧通知 ID 1 と token を引き継ぐ。
- 前回の全体通知時刻で設定間隔を守る。候補タスクは最後に通知した時刻がないもの、次にその時刻が古いものから選ぶ。同順位では従来の保留期限・最終完了・作成時刻・ID の順序を使う。
- 通知の「完了」はそのタスクの同日履歴を1回だけ記録し、そのタスクの通知をすべて消す。「保留」またはスワイプ削除はそのタスクの通知をすべて消し、操作から24時間候補から除外する。別タスクの通知は残す。通知タップだけでは状態を変えない。
- 同時表示は最大40件とし、上限では最も古い通知を消してから次を出す。OS の通知数制限に余裕を残すための上限であり、消した通知を保留操作とは扱わない。
- 次回処理には `AlarmManager.setAndAllowWhileIdle()` を使う。これは時刻予約であり、目覚まし音・専用画面・正確な時刻の権限は使わない。WorkManager の15分周期は復旧用に残す。再起動・時刻変更後は次の予約と評価を依頼する。強制停止後はアプリの手動起動が必要。
- OS と DB の通知を起動・評価時に照合する。予約済み／配信済みを区別し、古い token の操作は無視する。表示済み通知が OS 一覧から消えた場合は、スワイプ操作の通知が遅れても処理できるよう5分待つ。その後も操作が届かなければ、そのタスクを保留して通知を消す。
- スリープ中に時刻予約から起動された受信処理は、通知評価が終わるまで短時間の CPU WakeLock を保持する。画面点灯や目覚まし音は発生させない。

Android の inexact alarm は Doze 中の実行を許すが、実行時刻の上限を保証しない。[Android のアラーム選択指針](https://developer.android.com/develop/background-work/services/alarms)、[AlarmManager API](https://developer.android.com/reference/android/app/AlarmManager)

## 検証条件

固定時刻のテストで15分ごとの追加、未通知タスクの優先、遅延時の1件のみ追加、完了・保留の対象範囲、古い token、日付・時間帯、再起動時の照合を確認する。旧 DB からの移行、OS に複数件表示されること、while-idle 予約が目覚まし画面を持たないことも検証する。実際のスリープ中の通知頻度は端末と省電力設定ごとに観測が必要。
