# 保存結果と画面状態の境界の再設計

## 目的

ユーザーから、修正を繰り返してテストを通すだけでは変更容易性と運用性を損なう、との指摘を受けた。既存 MVP の機能を維持し、保存の成功条件と非同期操作の所有者を明示する。元の仕様は `2026-09-30-task-nudge-design.md`。

## 確認した設計上の問題

1. 保存完了を UI の観測値（タイトル・繰り返し）が一致するまで待つことで、項目追加が完了判定に波及する。観測が停止すると、確定済みの保存を失敗と表示したり、全操作を待たせ続けたりする。
2. タスク保存・設定保存・読み込みエラー・画面遷移が共通のフラグ群を使用し、別画面に古い成功・失敗が届く。
3. DB トランザクション確定後の通知整理や WorkManager 登録の例外が、保存失敗として呼び出し元へ伝わる。追加操作を再試行すると重複する。

## 比較と決定

| 方針 | 要件適合・モデル | 効率・並行性・耐障害性 | 変更容易性 |
|---|---|---|---|
| 現状へ条件を追加 | 個別のケースは直せるが、成功条件と所有者が暗黙のまま | 読み込み停止と保存確定後の失敗を区別できない | 新しい操作ごとに例外条件が増える |
| **境界を限定して再設計** | コマンドの確定、データ観測、画面所有者を分離 | 既存 Mutex とトランザクションを維持し、失敗の意味を正す | 状態と変更箇所を明示できる |
| 全体を再構築 | 現要件に対して新しい層や仕組みが増える | 移行と再検証の範囲が拡大 | 今回の問題に対する追加効果が乏しい |

境界を限定した再設計を採用する。Room、WorkManager、通知の世代 token、日付ポリシー、完了一意制約は維持する。ナビゲーション framework、イベント bus、汎用 command framework は追加しない。

## 不変条件

### 永続化

- `TaskRepository` のコマンド正常終了は DB トランザクションの確定を意味する。`saveTask` は確定した ID を返す。
- 保存前の失敗とトランザクション失敗は呼び出し元へ伝える。
- 確定後の通知整理・再評価予約の失敗は、確定済みコマンドを失敗に変えない。ローカルのログに、タスク本文を含めず記録する。
- 通知操作は引き続き共有 Mutex 内で直列化する。prepared 世代の確認と古い token の保護を維持する。
- コルーチンのキャンセルを成功や再試行可能な保存失敗へ変換しない。確定後に中断しても、定期実行・起動時の復旧で整合させる。

### 画面とコマンド

- 読み込み状態（最新 snapshot、読み込み中、読み込み失敗）は書き込み状態から独立する。画面移動や書き込みによって読み込みエラーを消さない。
- 読み込み失敗には明示的な「再読み込み」を用意し、購読を再開できるようにする。再試行しても購読を多重化しない。
- 各表示画面に明示的な session を持たせる。操作結果・操作エラー・それに伴う画面遷移は開始元 session にだけ適用する。メッセージを消す操作と所有者を切り替える操作を分ける。
- session 内の操作状態は `Idle / Saving / Committed(result) / Failed` のように排他的に表現する。`saving` と複数の成功フラグの組合せで表現しない。
- タスク編集と設定編集は、保存が確定した同じ session から再送信できない。保存前の失敗は再試行できる。
- 一覧の完了・停止・再開など、画面を離れず繰り返す操作は結果消費後に次の操作を受け付ける。
- DB 観測が遅れても、保存済みの追加を失敗に戻さない。新規タスクの表示待ちは「保存済み・データ表示待ち」として扱い、戻る操作と読み込み再試行を可能にする。全画面の書き込みを観測待ちで止めない。
- 保存成功のために入力フィールドの一致を待たない。タスク項目追加時に完了判定を修正する必要をなくす。
- 初期の存在しない通知 ID は安全に一覧へ戻す。確定済みの新規 ID の一時的な未観測とは区別する。
- 回転時の draft、画面、session の整合性を維持する。古い画面の成功・失敗が新しい draft を閉じたり置き換えたりしない。

## 検証する振る舞い

- 保存が確定し snapshot が遅れていても、再クリックで登録件数が増えない。
- 読み込みが失敗しても、確定済みの追加が「保存失敗」にならない。読み込み再試行で保存内容を表示できる。
- 保存中に別のタスク編集・設定編集へ移っても、新しい draft が古い結果やエラーで変わらない。
- DB 確定後に通知の取得・取消・再評価予約が例外になっても、返った保存結果が正しく、再評価で通知状態を回復できる。
- DB 確定前の失敗は保存失敗となり、保存されていない。
- 既存の通知世代・日付変更・履歴一意制約・入力・権限・回転のテストを保持する。観測値一致待ちという実装方式を要求するテストは、上記の利用者の振る舞いへ置き換える。

## 範囲外・後続確認

履歴集計クエリの最適化、通知状態の型の整理は今後の候補として記録する。今回の境界修正に一般化した基盤を追加しない。通知失敗のローカル診断は保存後処理の分離に含める。端末操作の実行と画面撮影は元の計画 Task 4 で行う。
